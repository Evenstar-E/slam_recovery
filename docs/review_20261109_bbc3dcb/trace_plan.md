# 下一步：group/sample 追踪的最小方案（先不改行为，等确认）

针对审阅 95c47e07 的意见：先**测**分组是否真的变，再做单因素控制；不再叠加 wait 机制。
本文件只提方案，不动代码。

## 0. 先说清楚现有 `DET_SYNC` 的问题（接受审阅的三点）

- `det_mtx_` 只是主循环的等待锁，**不是**回调写 buffer 的那把 `mtx_buffer`，两者无关联；
- 条件变量**没有 ready predicate**，`wait_for(20 ms)` 到期即返回，所以醒来的时刻仍是"某个 20 ms 网格 + 通知抖动"；
- `sync_packages` 消费的是**当时 buffer 里已有的内容**，因此 group 组成仍随到达时序变化；
- 证据：r1/r2 的 `imu_init_done iter` 是 **37 / 73**，消费的样本集不同。
  → 所以文档里不能再写"移除了墙钟相位"或"排除了 S3"。

## 1. 追踪方案（只加日志，不改任何计算/同步）

### 1.1 开关与输出

- 新编译开关 `TRACE_GROUP`（默认 OFF，与 `NO_MP`/`DET_SYNC` 同级）；
- 输出写到 `/tmp/fl_run_.../trace_group.csv`（路径由 runner 通过环境变量 `TRACE_GROUP_FILE` 传入，
  未设置则不写），每条事件一行、立刻 flush；**不新增任何锁**。

### 1.2 三类事件（字段都用现成变量，不引入新的共享状态）

| 事件 | 位置 | 字段 |
|---|---|---|
| `ARRIVE` | `standard_pcl_cbk` / `livox_pcl_cbk` 释放 `mtx_buffer` 之后 | 到达墙钟、header stamp、写完后 buffer 长度 |
| `GROUP` | `sync_packages` 成功返回后（主循环内） | `last_lio_update_time`、被消费组的 lidar 数、组内 IMU 样本数与首/末 stamp、image 帧数与 stamp、`imu_need_init` |
| `IMUINIT` | `IMU_init` 每次调用 + 结束时 | 迭代序号、本次组内 IMU 数与首/末 stamp、`MAX_INI_COUNT`、结束时总样本数 |

再加一条 `STATE`：每次处理完后 `_state.pos_end` / `rot_end` 的前 3 位，用来对齐"分歧从哪一帧开始"。

### 1.3 为什么这不改变行为

- 只在已有变量被计算之后读它们并格式化写盘；**不进入任何锁、不改变调用顺序、不改变 buffer 内容**；
- 代价是每次事件约几微秒的格式化，属于可测量的开销而非逻辑改变；两次 trace 运行之间仍然可能分叉
  （这正是要观测的），所以不能用"输出相同"来证明中性，只能用**代码审查 + 差异只有日志行**来证明。

## 2. 追踪能回答什么（判据先写死）

1. 同一 bag 两次，`GROUP` 的组成（组内 lidar 数、IMU 首末 stamp）是否不同？
   - **不同** → 分组确实是变量，进入 §3 的控制；
   - **相同** → 分组不是驱动因素，S3/S4 假设作废，按 BLOCKED 处理（见 §4）。
2. `IMUINIT` 的样本集是否两次不同（37 vs 73 的具体内容）？
3. 分歧首次出现在哪一个 `STATE` 之后（对应哪一帧、哪个 group）。

## 3. 若分组确实变化，两条单因素控制（届时只选一条）

- **方案 A：按消息时间的确定分组。** 让 `sync_packages` 严格按 header stamp 切分（一次只消费一帧 lidar
  及其之前的 IMU/image），并在相邻两帧之间不消费任何未到期消息。**代价**：需要动 `sync_packages` 的
  消费条件——这是宿主内部逻辑，且与 `mtx_buffer` 的加锁边界耦合，风险最高。
- **方案 B：回放屏障（推荐先做）。** 节点代码**完全不动**；由驱动侧把 `rosbag play` 变成按消息放行：
  节点每处理完一帧发布一个极小的标志（新增一个 topic，或复用现有日志），驱动侧收到后再放下一帧。
  **代价**：给节点加一个纯发布动作（行为中性），但把"到达时序"这个变量真正钉死；
  不改 buffer、不改锁、不改分组规则。

两条都要求：source/config/input/rate 冻结；receipt 同时记录 executable sha 与**运行时**从
`/proc/<pid>/maps` 取到的 `liblaser_mapping.so` 路径与 sha256。

## 4. 什么情况下直接判 BLOCKED（不再加机制）

任一条成立即停：

1. 追踪显示分组两次**相同**，但运行仍分叉 → 分组不是驱动因素，S3/S4 假设作废；
2. 方案 A 需要改动 `sync_packages` 与 `mtx_buffer` 的边界，而无法证明不引入数据竞争；
3. 方案 B 的屏障会让节点在等待时阻塞回调线程（同一 spinner），从而改变 `imu_prop` 定时器的行为。

第 2、3 条都属于"无法安全适配宿主"，按审阅要求转工程/机制复审，不再用 wait 机制堆补丁。

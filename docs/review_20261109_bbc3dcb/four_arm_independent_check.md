# 独立重算 four-arm 污染尾部与覆盖（reviewer 请求）

对照归档 `slam_recovery/experiments/manifests/four_arm_same_input_benchmark.json`（主树 `e6ae2de`）。
脚本：`verify_four_arm_independent.py`；**原始输出：`four_arm_independent_results.json`**（同目录，脚本直接写出）；
缓存回归测试：`test_verify_four_arm_cache.py`。

## 0. 结论先说

1. **四个数全部逐位复现**（4 位小数）：0.3647 / 0.9496 / 0.0079 / 0.9199。生产者手写网格与统计不是这些数字的来源，实现层面无缺陷。
2. **"跨运行 floor" 就是 A1 本身**——同一个谓词、同一份关键帧列表，`floor_ids == A1 ids`。A1 不可能超过它自己的 floor，两者 CI 重叠是同一份样本的自比较，不携带信息。
3. **四臂实际只有两张不同的地图**：A0 ≡ A2（同一 keyframe 列表），A1 ≡ A3（门控拒绝 → `verified_prefix=[]` → A3 退化为 A1）。表格里可用的独立观测只有 A0 对 A1 一组。
4. **bootstrap 按关键帧重采样，正确**。若按点重采样，CI 会窄 3.2–3.5 倍。
5. **代理面只由干净跑构建，未混入注入数据**；但 8.49M 干净点被截到 120k（1.4%），这个截断把两条尾部数都抬高了：A0 0.3647→**0.2966**，A1 0.0079→**0.0029**（全量代理面，各自的关键帧 bootstrap CI 见 §4.3）。
6. **结论方向支持**：全写比仅隔离的污染尾部高得多（未截断 0.2966 [0.2816, 0.3106] vs 0.0029 [0.0, 0.0085]，CI 分离），而且只换来 3.0 个百分点的覆盖。但这条结论在很大程度上由注入窗口后 12.9 m 的轨迹残差直接蕴含，属于一致性检查，不是独立的因果证据。

## 1. 独立了什么，共享了什么

| 环节 | 归档实现 | 本次实现 |
|---|---|---|
| bag 读取 | `rosbag` + 硬编码 24 字节 `VelodynePointXYZIR` dtype | `rosbags` + **消息自带 PointField 布局**（实测 `point_step=24`，`x@0,y@4,z@8`，与硬编码一致） |
| 时间戳 | `header.stamp` | `header.stamp`（同样不用 bag 记录钟） |
| 最近邻 | 手写 0.40 m 哈希网格 | `scipy.spatial.cKDTree` |
| 对齐 | 仓库 `umeyama_se3_align` + `associate_trajectories` | 自写 Umeyama SVD + 自写最近时间关联 |
| 统计 | `distance_stats` / `bootstrap_tail` | 自写 |

按协议保留（任务要求"同样的代理面、同样的对齐"）：输入 bag、0.5–30 m 距离滤波、
scan↔pose 配对规则（0.02 s 最近 / 0.075 s 内插）、每帧 250 点上限、代理面 120k 点上限、
注入前 SE(3) 目标。

**抽样范围：无关键帧抽样（no keyframe subsampling）。** 578 + 133 个关键帧全部计算，没有按帧抽。
但这**不是全点计算**：每帧仍截到 250 点、代理面仍是 8.49M 中的 120k、覆盖查询仍是 40k 预算。
§4.3 单独量了代理面截断的影响。

**bootstrap 的适用范围**：关键帧级重采样度量的是**条件采样误差**——固定这一对运行的前提下的估计波动。
它不是跨运行 / 部署泛化区间；要那个需要按运行分块的 block bootstrap 或多次重复运行。

## 4. 特别检查

### 4.1 floor 是不是 A1 本身 —— 是

生产者代码里 `floor_ids = [i for i in range(len(inj_kfs)) if inj_kfs[i]["ts"] < ONSET_ABS]`，
与 `A1 = list(range(len(pre)))`、`pre` 用同一个谓词，同一份列表。本次运行判定 `identical=True`。
所以：

- A1 与 floor 是**同一份样本**，CI 100% 重叠，重叠不构成任何证据；
- "每个臂必须超过 floor" 这条规则对 A1 是恒等式，不可用；真正有信息的是 A0 对 A1；
- A0 对 A1 的 CI 相距 0.33（[0.347, 0.381] 对 [0.004, 0.015]），不是"刚好分开"。

### 4.2 bootstrap 是否按关键帧 —— 是

生产者 `bootstrap_tail` 先算每帧尾部比例、再对**关键帧**重采样，实现正确。本次独立复现其 CI 逐位相同。
作为对照，若错误地按**点**重采样：

| 臂 | 关键帧 CI（正确） | 点级 CI（错误） | 宽度比 |
|---|---|---|---:|
| A0 | [0.3469, 0.3807] | [0.3622, 0.3671] | 3.5× |
| A1 | [0.0040, 0.0148] | [0.0068, 0.0088] | 3.2× |

按点重采样会把 CI 窄 3 倍以上——一帧内 250 个点高度相关。两者都只是条件采样误差（见 §1），
不是泛化区间。

### 4.3 代理面是否只由干净跑构建 —— 是，但有分辨率问题

- 构建路径只有 `cln_kfs`（干净 bag + 干净位姿），注入跑的点不进入代理面。
- 但干净跑共 **8 490 000** 点，生产者按全局 stride 截到 **120 000**（1.4%）。用全量点重算，
  并把关键帧 bootstrap 同样跑到全量分支（不借用 120k 的 CI）：

| 臂 | 120k 代理面 | 全量代理面 | CI（全量，关键帧 bootstrap） |
|---|---:|---:|---|
| A0/A2 尾部 >0.5 m | 0.3647 | **0.2966** | [0.2816, 0.3106] |
| A1/A3 尾部 >0.5 m | 0.0079 | **0.0029** | [0.0000, 0.0085] |

即：截断让两条尾部都偏高（方向保守），但幅度不小——头条数字 0.3647 比稠密代理面高 23%（相对），
而 A1 的 0.0079 是 0.0029 的 2.7 倍。**"污染尾部 0.0079" 里有三分之二是代理面采样，不是地图。**
两条未截断 CI 仍然分离（0.2816 > 0.0085）。

### 4.4 分解：36 pp 从哪来

A0 的关键帧列表是 A1 的超集，可直接切分：

| 子集 | keyframes | 尾部 >0.5 m @120k 代理面 | @全量代理面 |
|---|---:|---:|---:|
| 注入前（= A1） | 133 | 0.0079 | 0.0029 |
| 注入后（A1 不写的 445 帧） | 445 | **0.4714** | — |
| 全写（A0） | 578 | 0.3647 | 0.2966 |

覆盖：

| 地图 | 覆盖 @0.5 m |
|---|---:|
| 仅注入前 133 帧 | 0.9199 |
| 仅注入后 445 帧 | 0.6160 |
| 并集（A0） | 0.9496 |
| 差（在 40000 代理查询点上配对 bootstrap） | **+0.0297** [+0.0281, +0.0314] |

445 个被污染帧单独看能覆盖 61.6% 的代理面，但其中 58.6 pp 是 133 个干净帧已经覆盖过的，
净增只有 3.0 pp。这支持"多 36 pp 尾部只换 3 pp 覆盖"，同时说明 +3 pp 是**超集效应**，
不是"污染地图覆盖更好"。这个配对 bootstrap 按**代理点**重采样，相邻点在空间上相关，
所以它同样是条件采样误差，不是泛化区间。

## 5. 差异来源

按影响从大到小：

1. **代理面采样（唯一实质差异）**：120k/8.49M 截断，A0 +0.0681、A1 +0.0050。命中原因不是实现错误，
   而是代理面分辨率：120k 点均摊到 ~40 m × 走廊尺度，网格间隙可与 0.5 m 阈值相比。
2. **采样/配对/对齐**：全部一致到让结果逐位相同——点集 144500/33250、帧集 578/133、transform 一致
   （否则尾部不可能 4 位小数相同）。
3. **最近邻实现**：无差异。非零距离上的 KD-tree 与暴力搜索逐点相同。
4. **对齐**：自写 Umeyama 在 121 对注入前关键帧上拟合，`|t|=0.741 m`、转角 3.23°，与归档的臂级结果一致。

## 6. 缓存身份与输入身份（P2 修正）

- 缓存键 = **源 bag 的 sha256 + 过滤参数（topic / 0.5–30 m / 15000 上限）+ 脚本版本**，
  文件名即哈希；元数据里另存解码 layout 与全部参数，命中时**逐字段校验**，任何不一致就重建。
  拿 basename 当键、路径不存在也返回旧缓存的路径已不存在——`load_scans` 在查缓存前先 `os.path.exists`，
  缺失即 `FileNotFoundError`。
- 回归测试 `test_verify_four_arm_cache.py` 9 项全绿，覆盖：源内容变更换键、参数变更换键、
  脚本版本变更换键、同位置但内容身份不符的条目被拒、旧参数条目被拒、损坏文件被拒、
  **源路径不存在时即使有缓存也抛错**。
- 输入 sha256 与 manifest 不符时：写 `{"status": "INVALID_INPUT", ...}` 到结果 JSON 并 `exit 2`，
  不进入任何重算。已用一个改坏 hash 的 manifest 实测：注入位姿 hash 改成全 0 后停在 hashing 阶段，
  `SystemExit 2`，未产生 comparison。

## 7. 顺带发现的两处归档文字与代码不一致（不影响数字）

1. `onset_detection/head_frame_offset_sec = 0.0`，注释说"两套时间基重合"。按代码定义
   `inj_kfs[0].ts − first_common_abs` 重算是 **1.302695 s**（注入包头部 0–1.2 s 的 scan 无对应位姿被丢弃）。
   时间基本身确实重合（第一 raw scan == 第一 common scan == 1627785261.079），所以数字不受影响，
   但这个字段记录的量和它的注释讲的不是同一件事。
2. `alignment/residual_by_window/pre/n = 134`，而注入前关键帧只有 133 个（A1 的 133 个），
   对齐拟合实际只用了 121 对（12 个关键帧落在干净跑的 0–2.4 s 丢弃头部内，无 50 ms 内伙伴）。
   134 这个数不可能来自当前代码的同一次运行。同一块的 pre 均值 0.0401 m / p95 0.3137 m 也与
   拟合集上的 0.006 / 0.011 差两个数量级（那 13 个多出来的对子若平均 0.36 m 才能把均值拉到 0.04）。
   即：**残差表不是拟合的检验**，且与当前 onset 不自洽。

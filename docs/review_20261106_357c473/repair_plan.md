# 投稿前优先修复什么，怎样验证

**适用版本** [43119ed](https://github.com/Evenstar-E/slam_recovery/commit/43119edc0dbe4be486a16643548df8b899b7c117)。本文记录开发建议与通过条件。以下四组对照及新地点验证均待执行。

论文最值得证明的主张是：机器人发现退化时，能撤回已经写入的坏观测；面对一次可能修错的候选，能选择是否重新写图。已有结果给出了两个必须分别回答的问题。

- 在 `hall_01` 近场遮挡注入中，FAST-LIO2 原生轨迹 ATE 为 7.2760 m。直接修复和验证后修复均记录为 0.3058 m。这个例子支持修复器能改善轨迹；要测出验证的作用，还需要本会写坏地图的候选。
- 在独立的有真值表面仿真中，仅隔离与完整方法的最终体素污染率均为 0%。还需测重新写图后的有效覆盖，才能判断完整方法比持续隔离多恢复了多少有用地图。[现有轨迹与地图结果](../../slam_recovery/experiments/manifests/e2_ablation_b0_b7_and_r4_r5.json)

## 1. 先修提交与撤销的两个边界

| 优先项 | 当前可复现的行为 | 修改及验收 |
|---|---|---|
| 候选缺少证据 | 候选省略配对收益、Wilson 下界、重入位置跳变时，关键帧 42 被写入可信状态；同一候选显式填入坏值时被拒绝。 | 区分“缺测／通过／失败”，为每项证据绑定候选和测量来源。从正常候选入口各走一次。在其他条件合格时，仅实测通过允许提交；缺测则等待或拒绝，显式失败则拒绝。对照提交前后可信地图、因子及位姿版本。|
| 撤销最后一帧 | 撤销后可信位姿和体素均为零，下一次验证仍读到旧点 `[10, 0, 0]`。 | 撤销后以幸存关键帧刷新体素和验证点集，空集也应写回。分别撤销部分帧与全部帧，并从下一个候选的评分入口核对它实际收到的参考点。|

在仓库根目录运行 `python -B docs/review_20261106_a14bc1c/probe_boundaries.py` 可复现原行为。该脚本打印观测值；实施时将上表的通过条件写成断言，并覆盖正常节点调用。[构造默认值](../../slam_recovery/core.py#L171-L185) · [地图同步与候选评估](../../slam_recovery/sim/transaction_manager_node.py#L79-L258) · [边界探针](../review_20261106_a14bc1c/probe_boundaries.py)

## 2. 在估计候选前分开验证数据，在评分前锁定决策

- **扫描留出。** 当前 S1 重访案例用各帧扫描估计候选的横向位置，节点随后才从这些帧中每五帧取一帧打分。应在拟合前按扫描身份封存验证集，估计阶段只使用其余扫描和当时可用的运动信息。在留出时刻用该运动估计给出预测位姿。验收时核对拟合集与验证集的 ID 交集为空，并用一段非恒速运动检查恢复是否依赖固定步长。[候选生成](../../slam_recovery/sim/run_s1_s2_simulation_experiments.py#L261-L281) · [验证集选择](../../slam_recovery/sim/transaction_manager_node.py#L209-L239)
- **终点盲评。** Campus 脚本以首尾距离挑选快照并用同一距离评分。保留这个值作为“事后最优”参照；实际方法只能用提交时已取得的证据选候选。先落盘记录候选、快照、时刻和判决，再在统一终点评分，拒绝、等待和失败同样入表。[现有快照选择](../../slam_recovery/experiments/run_campus_and_overhead_benchmark.py#L69-L105)

## 3. 一次单宿主四组对照，分开修复器、隔离和验证的贡献

优先用已有 FAST-LIO2 和 `hall_01` 近场遮挡，前提是能导出宿主实际持久地图及提交记录。为同一段原始输入分别准备 clean 和 fault，对每种输入都执行下表。固定程序、初始化、传感器预算、输入时间戳、真值关联及最终评测时刻。让三组有检测的系统在同一事件开始干预，直接修复与完整方法复用同一候选、修正量、检查点及停修规则，以单独测出提交判决的影响。

| 组别 | 真实执行的动作 | 回答的问题 |
|---|---|---|
| A 原生 | 宿主按原方式估计并更新地图 | 故障造成多大损失，clean 能达到什么水平？ |
| B 仅隔离 | 撤回可疑写入，在预先约定的恢复写图条件下接续；跳过历史修复 | 单靠阻止污染，保住多少地图，漏掉多少覆盖？ |
| C 直接修复 | 对预先指定的同一候选执行修复并采用结果 | 修复器在有益与有害候选上分别会造成什么结果？ |
| D 验证后修复 | 执行 C 的候选，由冻结的证据规则决定提交、等待或拒绝 | 验证能挡下哪些有害写入，又会错过哪些有益修复？ |

预先登记候选集合与结局判定方式。至少覆盖有益修复、有害修复和 clean 自然匹配困难；若自然流程从未进入某类候选，可另列受控挑战，分别报告。用独立于门控分数的地图和轨迹评价各候选结局。将缺证据、未触发和未执行单列，保留全部分母。

一张结果表应同时给出以下数据：

- **地图**：实际提交过的污染写入数、最终污染率、相对独立参考的有效覆盖，以及撤销后重新获得的覆盖。注明参考来源、阈值和分母。仅能使用 clean 宿主地图时，明确标为代理参考。
- **轨迹**：共同实测时间支集上的位置误差、故障段与重入后误差、重入速度或位移尖峰、有效跟踪覆盖。无真值段保留缺测。使用辅助里程计构造的补点与原生跟踪分列。
- **决策及代价**：有害候选获准数／有害候选数、有益候选获准数／有益候选数、漏修、clean 报警与实际误干预、重新写图的等待时间。保存能连回同一候选和地图版本的逐事件日志。

## 4. 何时推进新地点，何时收窄论文

先在开发数据上登记地图、轨迹和 clean 安全的非劣化界限。比较 D 与 C 是否减少有害写入，比较 D 与 B 是否在保持地图质量的同时恢复了更多有效覆盖，并检查同一轮的轨迹和 clean 安全。若这三件事同时成立，冻结代码、参数和判定规则，在一个未用于训练、调参或选择规则的地点复测一次。已经反复查看的 `hall_02` 可保留作回归。

若主要收益只来自点云过滤，论文可聚焦“什么条件下污染剥离有效、什么条件下应拒绝修复”，并发布失败案例。第五宿主和新增模型放到能回答上述因果问题之后。[上一轮对实验计划的复审](README.md)

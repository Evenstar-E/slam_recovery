# 逐帧 LIO 耗时：归档状态

## 结论

`../README.md` §3u 写的"restore 前 2–18 ms、后 1–16 ms、整趟中位 12 ms、最大 1.066 s"
是**当时会话内的探针读数，原始逐帧记录没有落盘**。本归档目录里没有能复现这组数字的原件，
因此这一项标为 **NOT_ARCHIVED**。

不要把这一行当作可从归档核对的证据；归档里能核对的是同一段落的其它项
（received/applied、调度延迟、评估耗时、快照计数、两段完整走完），它们的原件都在。

## 为什么不能从现有文件重建

- `host.log` 里 `[ LIO ]` 行来自宿主的 `std::cout`，**没有时间戳**；两组 `[LIO] Raw feature num`
  之间无法取差。
- 有 ROS 时间戳的只有 `[ INFO] [..]` 行：每帧一条 `Get image, its header time:`（888 条）和
  帧边界的 `[NATIVE_CHECKPOINT] snapshot`（36 条）。它们给的是**帧到达/回合节拍**，不是 LIO 计算耗时。
- 本 run 没有录制 `/aft_mapped_to_init`，`ros_home_log/` 里也只有 rosout/master/roslaunch 三份日志。

## 能从归档算出来的近似量（不是 LIO 计算耗时）

用相邻两次 `snapshot` ack 的 `frame=` 增量与 applied 时间差：

| 量 | 值 |
|---|---|
| 采样区间数 | 29 |
| 帧周期 p10 / 中位 / p90 | 0.074 s / **0.111 s** / 0.216 s |

0.111 s 与 bag 的 10 Hz 相机/扫描节拍一致，是被**输入到达**限住的回合周期，不是单帧计算时间。
它只能说明"回合没有整体卡死"，不能替代 §3u 的那组毫秒数。

## 对结论的影响

§3u 用那组数字支持一句判断："本趟 restore 之后 LIO 并没有变慢，所以旧同步设计下的 30 s 超时
不是 LIO 变慢造成的。" 这个判断在**本归档内不可复核**；引用时应写成"当时会话内测得"，
或者干脆只用归档内可核对的事实：控制线程改造后四次 restore/resume 的 received 为 1–5 ms、
applied 为 0.19–0.59 s，调度延迟 0.006 / 0.119 s，两段均完整走完。

## 如果以后需要可归档的版本

宿主侧已有 `TRACE_GROUP` 编译分支（本 run 为 ON），但它写的是分组 trace，不含逐帧耗时。
要归档这一项，需要一次**新的**运行并显式启用逐帧耗时输出（例如给 `handleLIO` 加
`[LIO_TIMING]` 行并写时间戳），而不是从现有日志反推。
